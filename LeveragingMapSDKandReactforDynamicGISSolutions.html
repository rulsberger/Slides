Experience Builder Development

  • Widgets are strongly coupled with applications.
  • By making them more flexible, we can use them across projects.
  • We were having to write a lot of boiler plate to work with data-actions.
At Pierce County, our work with Experience Builder has been effective, and now we are looking at ways to build on that success: currently, Pierce County is developing custom widgets to replatform our applications from Web App Builder to Expereience Builder. And while we have had successes thus far, we are starting to experience the limitations of doing this work. As a fresh body working on these projects, I made a few observations which made me question our plan for development in EXB. - Widgets are strongly coupled with applications. -- this means that our logic is strongly related to our applications, meaning we are duplicating code that is specific to our apps. - By making them more flexible, we can use them across projects. - We were having to write a lot of boiler plate to work with data-actions. -- there is a lot of boiler plate that is necessary for us to work with Experience Builder Widgets. We are forced to use the ESRI choices for how to handle state management and other things.

Looking Ahead

While Experience Builder remains a great tool, we see opportunities to prepare for:

  • ESRI Maps SDK standalone development.
  • Avoiding unnecessary rework by future-proofing our work.
  • Building components that seamlessly transition into future projects.
So my teammates and I have agreed that Experience Builder may not be a long term solution. However, there is a concern about us replatforming our applications while our current applications are unsupported by ESRI. One thought is that get the applications built in expereience builder and then after we have moved off the ArcGIS Maps SDK 3x, then we can rebuild these applications with 4x API. However, that means that we are duplicating our work, and accumulating technical debt. We are creating work for ourselves in the future. We don't want to do that. So what are some ways that we can avoid this.

Proposed Solution

What if we proactively:

  • Develop reusable React components that work in both Experience Builder and standalone apps?
  • Reduce duplicate development while maintaining flexibility.
  • Standardize UI & logic across projects.
So the question is then, what if we could put our bets on both tools? Experience Builder is based on the Maps SDK, and it has allows for the integration of Calcite Components even though EXB doesn't utilize them in its own code. instead of putting all our eggs in on basket, could we build a pure React Component or in the future, our own web components and then incorporate them into Expereince Builder? Everything in theory says that this should work. And thankfully I had read some posts from when Experience Builder was newish about using React Components without the SDK in EXB. So the question was, could it be done with the widgets using the Maps SDK and Calcite? This would allow us to: - Avoiding unnecessary rework by future-proofing our work. - Building components that seamlessly transition into future projects, whether they are in EXB or a framework.

    Installing in Experience Builder

    Now let’s see how **Experience Builder can consume the component just like any other React project**. Instead of copying code manually, I can install the component directly from **our GitHub repo**. npm install git+https://ryanulsberger@bitbucket.org/piercecountywa-ss/react_components.git#Deploy - This means **Experience Builder can now use our reusable components**, but so can **any other React-based project**. - We don’t have to rewrite the same logic multiple times—we can **share updates easily** across all apps. I also want to highlight that I learned that there are ways to share code between widgets that I just learned about from the Dev Summit. The difference is that in EXB I have to follow an exact folder structure to make the code accessible, and in this method, I can keep my components outside of the EXB Ecosystem making them more accessible to use in Pure React Apps.

    So to debug this, I started with what any reasonable person would do. Ask ChatGPT. ChatGPT suggested that I actally had two different versions of the Maps SDK installed. But as I showed earlier, I knew that I needed to have the versions of the Maps SDK for Javascript explicitly set to match the version of Expereience Builder. So I had already covered these bases. I then opened a software support ticket with ESRI, and they were able to replicate the behavior, but also were unable to provide any explainations. Thankylly, I attened the Developer Summit which I was able to learn that Experience Builder utilizes the CDN for calling the Maps SDK and Calcite. So when I load packages that utilize the Maps SDK even as a peer dependency, my components are still looking for the physical location of these files. The reason I get a half working application is that the the JimuMapView is instantiated with the CDN first before the IdentifyAll widgets. That's why I am getting a peice-meal working widget. Special thanks to Rene for helping narrow down this issue.
