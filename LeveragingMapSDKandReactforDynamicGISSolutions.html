The Problem

Web App Builder and the ArcGIS Maps SDK V.3

The problems we're facing at Pierce County are not unique to us. At the ESRI Developer Summit, one question was raised consistently throughout the discussions: "Now that Web AppBuilder and the ArcGIS Maps SDK for JavaScript 3.x are reaching their end of support, what should I be doing for my future application development?" This is a key concern that resonates with many organizations, including Pierce County, which currently maintains around 12 different applications—all built with Web AppBuilder. My team is in the midst of replatforming these applications to ensure they continue to meet our needs and remain functional moving forward.

The Big Question: *click* Experience Builder *click* vs. *click* Custom Applications So, here we are—facing a big decision. On one side, we have Experience Builder, and on the other, we have custom applications using the new Maps SDK. So far, we’ve migrated some of our applications to Experience Builder, but the question remains: Is this really the best long-term strategy for our needs?

Experience Builder Development

  • Widgets are strongly coupled with applications.
  • Lack of flexibility across projects.
  • ExB applications are harder to keep up-to-date.
At Pierce County, we've had success with Experience Builder (ExB), but as we develop custom widgets to replatform applications from Web App Builder, we’re starting to hit some limitations. As someone new to the team, I’ve observed a few things that raised questions about our development strategy with ExB: *Click* Our app-specific logic is tightly tied to the widgets, leading to duplicated code across projects. *Click* To make widgets more reusable across projects, we need to increase their flexibility. *Click* Because ExB is a no-code/low-code environment, it can be more challenging to apply updates, especially with custom widgets, compared to custom-built applications where we have more control over versioning and dependencies.

Looking Ahead

While Experience Builder remains a great tool, we see opportunities to prepare for:

  • ESRI Maps SDK standalone development.
  • Avoiding unnecessary rework by future-proofing our work.
  • Building components that seamlessly transition into future projects.
After discussing with my teammates, we’ve agreed that Experience Builder may not be the long-term solution. However, there’s a concern about replatforming while our current applications are unsupported by ESRI. *click* One option is to build our applications in Experience Builder now, and once we've moved off the ArcGIS Maps SDK 3.x, we can rebuild them using the 4.x API. But, this approach means duplicating work and accumulating technical debt. We would be creating extra work for ourselves in the future, and we want to avoid that. So, how can we avoid this? What’s the best approach to minimize this future workload?

💡 Proposed Solution

What if we proactively:

  • ⚛️ Develop reusable React components that work in both Experience Builder and standalone apps.
  • 🔄 Reduce duplicate development while maintaining flexibility.
  • 🎨 Standardize UI & logic across projects.
What if we could bet on both tools? Experience Builder is built on the Maps SDK and supports Calcite Components, even though it doesn’t use them in its core code. Instead of relying on just one platform, could we create pure React components (or custom web components in the future) and integrate them into both Experience Builder and custom apps? Theoretically, this should work. I found posts from when Experience Builder was first released about using React components in EXB without the SDK. The main challenge is whether we can do this with widgets that use the Maps SDK and Calcite. By doing this, we can avoid unnecessary rework by future-proofing our work and build components that seamlessly transition into future projects—whether in EXB or custom frameworks.

Why Reusable React Components?

Key benefits:

  1. Reduce duplicate development
  2. Ensure smooth future transitions
  3. Test Developments Independently of Experience Builder
*click* By developing reusable React components, we’re able to avoid recreating the same functionality for each project. This reduces the time and effort spent on duplicate development, making our team more efficient. *click* By adopting a modular approach, we’re also future-proofing our work. Whether we transition to a new version of the Maps SDK or shift our focus to another platform, our components are designed to adapt without significant rework. *click* Additionally, by testing these components outside of Experience Builder, we can validate how they function within the Maps SDK environment. This ensures that the components are versatile, working both within Experience Builder and standalone apps.

    Unfortunately, I don’t have my own ArcGIS license, so I can’t pull up a working version of Experience Builder to demo this part directly. But I can confirm that it does work—just not 100%. Let’s talk about some of the challenges I encountered when integrating this widget into Experience Builder. Here’s what’s happening: ✅ The widget itself renders correctly—so the React integration is working. ⚠️ However, some parts of the Sketch widget and FeatureList aren’t behaving as expected. The Sketch widget does not display the geometry on the map. But interestingly, it still executes queries against the WebMap, as in, I can see the results being returned when logged to the console. The issue seems to be related to how certain parts of the Maps SDK interact within the Experience Builder environment. I also start seeing some errors coming from different Maps SDK modules when trying to render certain elements. Instance of 'esri.Graphic' which is not a subclass of 'esri.Graphic'? What does that mean? This means that while our approach is fundamentally on the right track, we need to troubleshoot how Experience Builder manages specific SDK components packages.
    • 🤖 ChatGPT
    • 🔍 ESRI Support
    • 🧑‍💻 Ask a Dev
    So, when I ran into these issues, I did what any reasonable person would do—I asked ChatGPT. ChatGPT suggested that the issue might be due to conflicting versions of the Maps SDK. That made sense initially, but I had already explicitly set the Maps SDK version to match the version used by Experience Builder. So that theory was a dead end. Next, I reached out to ESRI support. They were able to replicate the behavior, which confirmed that it wasn’t just something in my environment. But since this was debugging my own custom code, they weren’t able to provide further assistance. That left me with one final option: the ESRI Developer Summit. And this is where I finally found the missing piece. At the summit, I learned that Experience Builder loads the Maps SDK and Calcite via a CDN, rather than expecting local installations. Here’s what that means: Even though my components include the Maps SDK (even as a peer dependency), they are still looking for a local file path rather than loading from the CDN. This is why my widget partially works—the JimuMapView initializes using the CDN before the IdentifyAll widget loads. The result? A half-functional widget that can query layers but doesn’t fully render. A special thanks to Rene for helping narrow down this issue!"
